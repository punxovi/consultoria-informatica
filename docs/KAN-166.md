# KAN-166: formulario de Programas

Implementación reconstruida desde `sprint-3` (`b8c4ee1`) con la dependencia KAN-171 (`6ee81aa`). No incorpora los commits de la implementación anterior de KAN-166. El PR debe apuntar a `sprint-3`; integrar primero el PR de KAN-171 evita revisar dos veces sus cambios.

## Comportamiento

- Crear en `/programas/nuevo` y editar en `/programas/<uuid>/editar`, con componentes compartidos Input, Button y Card y acceso de interfaz ADMIN.
- Campos obligatorios y límites según el schema compartido de las Actions. Errores junto al campo y resumen accesible.
- Líneas de acción dinámicas con su resultado esperado, mínimo una, máximo 50, sin nombres repetidos.
- Referencias ODS/ESG opcionales, persistidas como texto; se pueden vaciar al editar.
- JPG/PNG/WebP de hasta 10 MB, conversión en navegador a WebP menor a 600.000 bytes y máximo 2000 px, vista previa y almacenamiento privado con URL firmada de cinco minutos.
- Cancelación con confirmación si hay cambios, indicador de carga, bloqueo durante guardado y confirmación visible sin redirección automática.
- El catálogo y el detalle consultan las Actions y utilizan UUID reales. Se eliminan los datos ficticios de esas vistas.
- Las llamadas llevan la sesión Bearer. RLS y los permisos de la base siguen siendo la barrera de autorización.
- Si falla la imagen después de crear, el formulario conserva ID y versión para reintentar como edición; no vuelve a crear el programa.
- Botón «Eliminar programa» en el detalle, visible a ADMIN, con confirmación, carga y control de versión. Marca `archived_at` y conserva planes, líneas e imágenes. Desaparece del catálogo activo. Usa los permisos RLS existentes y no necesita una migración adicional.

## Dependencias para probar con Supabase

Aplicar las migraciones del repositorio en orden en el entorno de pruebas, incluidas las de relaciones de Programas, líneas de acción y Storage. Esta implementación necesita además `supabase/migrations/20260924120000_fge_programas_referencias.sql`. No se aplicaron migraciones a la base remota durante el desarrollo.

Configurar `frontend/.env` usando `.env.example`. Iniciar sesión con una cuenta ADMIN del entorno de pruebas. No usar service-role en el navegador.

La ausencia de migraciones debe corregirse en la base; no se convierte una falla de la tabla de líneas en un guardado silencioso sobre columnas antiguas.

## Reproducir la prueba del navegador

Con el servidor de producción local iniciado (`npm run build`, luego `HOST=127.0.0.1`, `PORT=4322`, `npm start` según la sintaxis del shell), ejecutar `node scripts/qa-programas.cjs` desde `frontend`.

El script requiere Playwright disponible (o `PLAYWRIGHT_MODULE` con su ruta), Edge instalado y `.env` con la URL pública del proyecto. Se pueden configurar `BASE_URL`, `BROWSER_CHANNEL` y `QA_OUTPUT`. Intercepta las llamadas a Supabase y Actions: no escribe datos remotos ni usa credenciales de usuarios reales.

## Límite de la dependencia KAN-171

Las Actions existentes guardan Programa y líneas en llamadas separadas. Una falla intermedia puede dejar una operación parcial; este formulario no transforma esas operaciones en una transacción. Ante un error de guardado o conexión se debe comprobar el registro antes de repetir una creación. Resolver atomicidad y sincronización por identidad de línea corresponde a revisar el contrato de esa dependencia antes de considerar el flujo listo para producción.

La carga inicial de los seis programas y la administración de planes son otros alcances de HU03. La eliminación solicitada posteriormente se implementa como archivo lógico del programa.
